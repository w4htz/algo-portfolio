## 1. Заказы за сутки, `n ≤ 200 000`

Есть ли среди номеров хотя бы два одинаковых?

- **Проходит:** \(O(n)\) по времени, \(O(n)\) по памяти.
- **Решение:** Использовать хэш-таблицу (множество `set` в Python). Проходим по списку один раз: если элемент уже есть в множестве, то дубликат найден, иначе добавляем его туда.
- **Что мешало проще:** Обычный перебор «в лоб» двойным циклом сравнивает каждый элемент с каждым. Это дает сложность \(O(n^2)\), что при текущем ограничении приведет к зависанию программы.
- **Почему это верно (с числом):** Перебор «в лоб» потребует порядка \(n^2 / 2 = 200\,000^2 / 2 = 2 \cdot 10^{10}\) операций. При ориентире \(10^7\) оп/сек выполнение займет **2000 секунд**. Линейное решение через `set` выполнится за \(200\,000\) операций (менее **0.02 секунды**).

## 2. Цены на складе, `n ≤ 100 000`

Найти три самые дешёвые позиции.

- **Проходит:** \(O(n)\) по времени, \(O(1)\) по дополнительной памяти.
- **Решение:** Пройти по списку цен ровно один раз, поддерживая три переменные для хранения текущих трех минимумов (обновляя их по ходу итерации).
- **Что мешало проще:** Полная сортировка массива через `sorted(prices)[:3]` работает за \(O(n \log n)\). Хоть она и укладывается в лимит времени, она делает лишнюю работу и создает копию массива в памяти.
- **Почему это верно (с числом):** Сортировка всего массива потребует около \(n \log_2 n = 100\,000 \cdot 17 \approx 1.7 \cdot 10^6\) операций. Это укладывается в секунду, но предложенный проход с тремя переменными сделает ровно \(100\,000\) итераций, что в **17 раз эффективнее** и не требует выделения памяти \(O(n)\).

## 3. Архив чеков `n ≤ 10⁷`, запросов `q ≤ 10⁵`

Отсортирован. По каждому запросу сказать, есть ли такой чек.

- **Проходит:** \(O(q \log n)\) по времени, \(O(1)\) по памяти.
- **Решение:** Поскольку архив чеков уже отсортирован, для каждого из \(q\) запросов необходимо применить алгоритм бинарного поиска (`binary search`).
- **Что мешало проще:** Обычный линейный поиск (`if target in receipts`) для каждого запроса имеет общую сложность \(O(q \cdot n)\), что при данных объемах вызовет огромное превышение лимита времени.
- **Почему это верно (с числом):** Линейный поиск на каждый запрос потребует в худшем случае \(q \cdot n = 10^5 \cdot 10^7 = 10^{12}\) операций (это **100 000 секунд** ожидания). Бинарный поиск сделает для одного запроса максимум \(\log_2(10^7) \approx 24\) операции, а для всех запросов суммарно — всего \(2.4 \cdot 10^6\) операций, что строго меньше \(10^7\).

## 4. Координаты курьеров, `n ≤ 3 000`

Найти двух ближайших друг к другу.

- **Проходит:** \(O(n^2)\) по времени, \(O(1)\) по памяти.
- **Решение:** Найти расстояние между всеми парами курьеров с помощью вложенного цикла (перебор всех сочетаний) и обновить глобальный минимум.
- **Что мешало проще:** Более быстрые алгоритмы (например, метод разделяй-и-властвуй за \(O(n \log n)\)) гораздо сложнее в реализации. Небольшое ограничение на размер \(n\) позволяет написать простой и надежный полный перебор.
- **Почему это верно (с числом):** Количество пар для проверки составляет \(n(n - 1) / 2 \approx 3000^2 / 2 = 4.5 \cdot 10^6\) операций. Это **меньше ориентира в 10 000 000 операций**, поэтому алгоритм гарантированно выполнится в пределах одной секунды.

## 5. Одно число `k ≤ 10⁹`

Сколько раз его можно разделить пополам до единицы?

- **Проходит:** \(O(\log k)\) по времени, \(O(1)\) по памяти.
- **Решение:** Использовать цикл `while k > 1: k //= 2` со счетчиком шагов, либо встроенный метод `.bit_length() - 1` для подсчета количества бит.
- **Что мешало проще:** Альтернативный перебор вычитанием единицы за \(O(k)\) до нуля здесь невозможен, так как само число слишком велико.
- **Почему это верно (с числом):** Если бы мы уменьшали число последовательным вычитанием, это заняло бы до \(10^9\) операций (**100 секунд**). Деление пополам (логарифмический рост) для числа \(10^9\) потребует максимум \(\log_2(10^9) \approx 30\) операций, что выполняется мгновенно.

## 6. Две накладные, `n ≤ 10⁵` и `m ≤ 10⁵`

Обе отсортированы. Собрать из них один отсортированный список.

- **Проходит:** \(O(n + m)\) по времени, \(O(n + m)\) по памяти.
- **Решение:** Использовать алгоритм слияния двумя указателями (как в Merge Sort). Сравниваем текущие элементы накладных, меньший заносим в результат и сдвигаем указатель.
- **Что мешало проще:** Простое слияние «в лоб» через `sorted(left + right)` имеет сложность \(O((n+m) \log(n+m))\), что выполняет лишнюю работу, полностью игнорируя факт изначальной отсортированности списков.
- **Почему это верно (с числом):** Сортировка объединенного массива сделает около \(200\,000 \cdot \log_2(200\,000) \approx 200\,000 \cdot 18 = 3.6 \cdot 10^6\) операций. Метод двух указателей сделает ровно \(n + m = 100\,000 + 100\,000 = 200\,000\) операций сравнения, что в **18 раз быстрее** и эффективнее.
